FFmpeg 동시 실행으로 인한

01 · OVERVIEW

개요

gif lower는 사용자가 업로드한 GIF 파일을 FFmpeg로 변환해 용량을 줄인 결과물을 제공하는 서비스입니다. 변환 기능 자체는 정상적으로 동작했지만, 여러 요청이 동시에 들어오는 상황에서는 FFmpeg 프로세스가 한꺼번에 실행될 수 있는 구조였습니다.

02 · PROBLEM

문제 상황

각 변환 요청은 CPU를 많이 사용하는 FFmpeg 작업을 생성합니다. 요청 하나만 처리할 때는 문제가 없었지만, 여러 사용자의 요청이 겹치면 실행 중인 프로세스가 증가하고 API 서버까지 영향을 받을 가능성이 있었습니다.

03 · OBSERVATION

관찰한 현상

  • 요청마다 별도의 FFmpeg 프로세스가 생성됐습니다.
  • 변환 작업의 실행 시간 동안 CPU 사용량이 증가했습니다.
  • 실행 중인 작업 수를 제한하는 장치가 없었습니다.
  • API 요청 처리와 파일 변환 작업이 같은 흐름 안에서 실행됐습니다.
수치가 남아 있지 않은 부분은 임의로 만들지 않았습니다. 확인 기준은 요청 수, FFmpeg 프로세스 수, 작업 완료 여부와 일반 API 응답 가능 여부였습니다.
04 · HYPOTHESIS

처음 세운 가설

  • 파일 업로드 크기가 지나치게 큰지
  • 네트워크 전송 시간이 병목인지
  • FFmpeg 프로세스 우선순위가 높은지
  • 동시 실행되는 프로세스 수가 자원을 경합하는지
05 · VERIFICATION

확인 과정

단일 요청과 동시 요청을 나눠 실행 중인 FFmpeg 프로세스 수와 작업 완료 흐름을 비교했습니다. 파일 하나의 처리보다 요청이 겹칠 때 실행 프로세스가 함께 증가하는 구조를 우선 확인했습니다.

확인 흐름: 단일 요청 → 동시 요청 → 프로세스 수 비교 → 일반 API 응답 여부 확인
06 · ROOT CAUSE

실제 원인

문제의 원인은 FFmpeg 자체가 아니라 CPU 집약적인 작업을 제한 없이 동시에 실행할 수 있는 구조였습니다. HTTP 요청이 들어올 때마다 변환 작업을 바로 시작했기 때문에 요청 수가 실행 중인 프로세스 수로 이어질 수 있었습니다.

07 · OPTIONS

검토한 해결 방법

  1. 파일 업로드 크기만 제한하는 방법
  2. 일정 수 이상의 요청을 바로 거부하는 방법
  3. FFmpeg 프로세스의 우선순위를 낮추는 방법
  4. 작업 큐를 두고 동시 실행 수를 제한하는 방법
08 · ACTION

선택한 조치

변환 요청을 바로 실행하지 않고 작업 큐에 등록하도록 변경했습니다. 실행 중인 변환 작업 수를 제한하고 작업이 끝난 뒤 다음 작업을 처리하도록 구성했습니다.

const queue = [];
let activeJobs = 0;
const maxConcurrentJobs = 2;

function enqueue(job) {
  queue.push(job);
  processNext();
}

async function processNext() {
  if (activeJobs >= maxConcurrentJobs || queue.length === 0) return;

  const job = queue.shift();
  activeJobs += 1;

  try {
    await runFfmpeg(job);
  } finally {
    activeJobs -= 1;
    processNext();
  }
}
09 · RESULT

결과

  • 동시에 실행되는 FFmpeg 작업 수를 제한했습니다.
  • API 요청 처리와 CPU 집약적 변환 작업의 실행 흐름을 분리했습니다.
  • 서버 자원이 특정 시점에 집중되는 위험을 줄였습니다.
  • 재시도, 대기 상태, 작업 만료 기능을 추가하기 쉬운 구조가 됐습니다.
검증 결과: 대기 작업과 실행 작업이 분리되고, 실행 중인 FFmpeg 프로세스 수가 설정값 안에서 유지됩니다.
10 · PREVENTION

재발 방지

CPU 집약 작업을 추가할 때 동시성, 대기열, 실패 처리, 임시 파일 정리 시점을 기능 구현과 함께 검토하도록 기준을 남겼습니다.

11 · NEXT

남은 개선점

현재 구조는 단일 서버의 메모리 내 작업 큐를 기준으로 합니다. 서버가 재시작되면 대기 중인 작업 정보가 사라질 수 있으므로 향후 Redis 기반 큐나 별도 Worker 구조로 분리할 수 있습니다.

12 · LEARNING

배운 점

기능이 정상적으로 실행되는 것과 운영 환경에서 안전하게 실행되는 것은 다른 문제였습니다. CPU 사용량이 큰 작업은 요청 처리와 분리하고 서버가 감당할 수 있는 범위 안에서 실행되도록 제어해야 한다는 점을 확인했습니다.
