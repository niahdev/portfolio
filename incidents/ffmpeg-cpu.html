INCIDENT 01 · gif_lower

FFmpeg 동시 실행으로 인한
서버 CPU 부하

요청과 무거운 작업의 실행을 분리하고 서버가 감당할 수 있는 동시 처리 범위를 코드로 제한한 기록입니다.

Node.jsFFmpegJob QueueDocker
01 · PROBLEM

여러 변환 요청이 동시에 들어오면 서버 전체 응답이 느려졌습니다.

gif_lower는 업로드된 파일을 FFmpeg로 변환합니다. 단일 작업은 완료됐지만 여러 사용자의 요청이 겹치는 조건에서 처리 시간이 늘어나고 일반 API 응답까지 영향을 받았습니다.

02 · OBSERVATION

요청 수와 FFmpeg 프로세스 수가 함께 증가했습니다.

단일 요청과 동시 요청을 나눠 실행 중인 프로세스 수, 작업 완료 여부, 컨테이너 자원 상태를 비교했습니다. 네트워크보다 CPU를 사용하는 변환 프로세스가 겹칠 때 문제가 재현됐습니다.

확인한 신호: 동시 요청 수 · 실행 중인 FFmpeg 프로세스 수 · 작업 완료 여부 · API 응답 가능 여부
03 · HYPOTHESIS

파일 크기 자체보다 무제한 병렬 실행을 우선 의심했습니다.

기존 구조는 업로드 요청이 들어올 때마다 FFmpeg를 즉시 시작했습니다. 파일 크기와 관계없이 요청 수만큼 CPU 집약적인 프로세스가 생성되는 구조였습니다.

04 · ROOT CAUSE

HTTP 요청과 변환 작업의 실행 경계가 없었습니다.

요청을 접수하는 계층이 서버의 현재 작업 수를 고려하지 않고 바로 프로세스를 생성했습니다. 비동기 API였지만 자원 사용량 자체를 제한하는 장치는 없었습니다.

05 · FIX

작업 큐와 동시 실행 제한을 추가했습니다.

업로드 요청은 작업을 등록하고, 큐의 작업자가 정해진 개수만 가져가 FFmpeg를 실행하도록 변경했습니다. IP별 작업 생성 제한과 완료·실패 시 임시 파일 정리도 함께 적용했습니다.

  • HTTP 요청과 FFmpeg 실행 분리
  • 동시에 실행할 변환 작업 수 제한
  • IP별 생성 제한과 임시 파일 자동 정리
06 · RESULT

동시 요청이 들어와도 실행 프로세스 수가 설정 범위를 넘지 않습니다.

남은 작업은 큐에서 순서를 기다리고 일반 요청을 처리할 자원을 남길 수 있게 됐습니다. 정확한 성능 수치를 과장하지 않고, 동시 실행 상한이 지켜지는 동작으로 개선을 확인했습니다.

검증 결과: 대기 작업과 실행 작업이 분리되고, 실행 중인 FFmpeg 프로세스 수가 설정값 안에서 유지됨
07 · PREVENTION

무거운 외부 프로세스에는 수명 주기와 제한을 함께 설계합니다.

이후 CPU 집약 작업을 추가할 때 동시성, 대기열, 실패 처리, 파일 정리 시점을 기능 구현과 함께 검토하도록 기준을 남겼습니다.
