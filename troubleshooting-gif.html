01
OBSERVE · 관찰

먼저 재현 조건을 나눴습니다.

서로 다른 GIF 파일을 한 번에 하나씩 요청했을 때와 여러 요청을 동시에 보냈을 때를 비교했습니다. 단일 작업은 정상적으로 끝났지만 요청이 겹치면 처리 지연과 자원 사용 증가가 함께 나타났습니다.

확인한 신호동시 요청 수 · 실행 중인 FFmpeg 프로세스 수 · 컨테이너 자원 상태 · 작업 완료 여부
확인
02
HYPOTHESIS · 가설

파일 크기보다 동시에 실행되는 프로세스 수가 문제라고 판단했습니다.

기존 구조는 업로드 요청이 들어올 때마다 FFmpeg 작업을 즉시 시작했습니다. 따라서 파일 크기와 관계없이 요청 수만큼 무거운 프로세스가 생성되고, CPU와 메모리를 서로 차지하는 구조였습니다.

네트워크 지연 가능성 낮음파일 크기만의 문제 불충분프로세스 자원 경합 핵심 원인
좁히기
03
EXPERIMENT · 검증

실행 개수를 제한하고 같은 조건을 반복했습니다.

요청을 즉시 실행하는 대신 대기열에 넣고, 서버가 동시에 처리할 수 있는 작업 수를 제한했습니다. 같은 방식으로 요청을 반복했을 때 나머지 작업은 실패하는 대신 순서대로 대기했고 서버가 다른 요청에 응답할 여유를 유지했습니다.

04
FIX · 해결

작업 큐만이 아니라 요청 진입과 파일 수명까지 함께 제한했습니다.

동시 처리 수 제한, IP별 작업 생성 제한, 완료·실패한 임시 파일의 자동 정리를 함께 적용했습니다. 하나의 보호 장치에 의존하지 않고 작업이 들어오는 시점부터 종료된 이후까지 자원 사용 범위를 통제했습니다.

01동시 FFmpeg 작업 수 제한
02IP별 요청 생성 제한
03임시 파일 자동 정리
해결
05
LEARN · 회고

비동기 처리가 곧 자원 제어를 의미하지는 않았습니다.

백그라운드에서 실행하도록 분리해도 무거운 프로세스의 개수를 제한하지 않으면 서버 자원은 그대로 고갈될 수 있습니다. 이후 외부 프로세스를 사용하는 기능은 구현 전에 동시성 한도, 대기열, 실패 처리, 정리 시점을 함께 설계합니다.

무거운 작업에서는 “빨리 시작하는 것”보다 “감당할 수 있는 만큼 실행하는 것”이 서비스 전체의 안정성을 지킨다.
